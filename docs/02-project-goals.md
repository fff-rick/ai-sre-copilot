# 项目目标

## 1. 产品愿景

让值班工程师在一个界面中获得可验证、可追踪、可安全接管的故障调查结果，将 AI 从“解释日志的聊天工具”升级为“遵循运维边界的调查协作者”。

## 2. V1 总目标

在一个可重复部署和注入故障的测试环境中，实现从告警接入、证据采集、根因假设、假设验证、人工审批到恢复验证的完整闭环，并使用自动化数据集证明系统的正确性、安全性、可靠性、延迟和成本。

## 3. 功能目标

### G-F01 告警与调查管理

- 支持通过 HTTP/Webhook 创建调查。
- 保存告警来源、时间范围、服务、严重程度和标签。
- 支持查询调查状态、步骤、证据、结论和审批记录。
- 支持取消、失败重试和中断后恢复。

### G-F02 多源证据采集

至少实现以下只读工具：

1. Prometheus 即时查询。
2. Prometheus 区间查询。
3. Loki 日志查询。
4. Tempo Trace 查询。
5. Kubernetes Pod/Deployment 状态查询。
6. Kubernetes Event 查询。
7. 最近发布记录查询。
8. Git Commit/Diff 查询。
9. Runbook 检索。
10. 历史事故检索。

### G-F03 根因调查

- 生成一份显式调查计划。
- 并发收集互不依赖的数据源。
- 生成最多 3 个候选根因假设。
- 为每个假设记录支持证据、反证、置信度和待验证项。
- 通过进一步工具调用验证或否定假设。
- 信息不足时明确输出“不确定”，不得虚构证据。

### G-F04 处置与审批

- 对建议操作标注只读、低风险变更和高风险变更。
- 所有状态变更操作必须进入人工审批。
- 审批人可以批准、修改或拒绝。
- 执行前再次校验操作者、目标资源、参数、有效期和幂等键。
- V1 验收仅要求在隔离测试环境执行重启、扩缩容和回滚。

### G-F05 结果呈现

- 展示事故摘要、影响范围、时间线和调查进度。
- 展示根因 Top-3 与置信度。
- 每条关键结论可以跳转到证据来源。
- 展示模型调用、工具调用、Token、延迟和错误。
- 自动生成结构化复盘草稿。

### G-F06 评测与回放

- 维护版本化故障数据集。
- 回放固定告警和工具响应。
- 支持比较模型、Prompt、检索策略和工具版本。
- 输出 JSON 与 Markdown 评测报告。
- 任一强制安全用例失败时阻止发布。

## 4. 非功能目标

### G-N01 正确性

- 关键结论必须引用证据 ID。
- 结构化输出必须通过 Schema 校验。
- 确定性事实优先由规则或工具结果计算，不由 LLM 猜测。

### G-N02 安全性

- AI 服务不持有 Kubernetes 管理员凭据。
- Go 工具网关默认只读，并执行最小权限 RBAC。
- 所有变更工具必须验证审批令牌。
- Prompt、工具参数和工具结果均进行长度、格式和敏感信息处理。
- 未审批、过期审批、目标不一致和重复执行均应被阻断。

### G-N03 可靠性

- 每个外部调用设置超时、有限重试和错误分类。
- 调查状态持久化，服务重启后能够从最近检查点恢复。
- 工具写操作具备幂等性。
- 单个数据源不可用时，系统应降级并明确标记缺失证据。

### G-N04 可观测性

- 为 HTTP、Agent 节点、模型、检索、gRPC 和工具执行创建关联 Trace。
- 记录首 Token 延迟、模型耗时、工具耗时、Token、错误率和调查总时长。
- Prompt 与工具结果默认脱敏，原始敏感内容不得直接进入普通日志。

### G-N05 可维护性

- Python 与 Go 通过版本化 Protobuf 契约通信。
- 模型、检索器、工具和存储通过接口隔离。
- 核心领域类型不直接依赖模型厂商 SDK。
- 配置与密钥分离，密钥不得提交到仓库。

## 5. V1 量化成功标准

以下指标均基于冻结的验收数据集计算：

| 指标 | V1 门槛 | 说明 |
|---|---:|---|
| 故障用例数量 | >= 30 | 至少覆盖 8 类故障 |
| 调查完成率 | >= 90% | 未因未处理异常中止 |
| 根因 Top-1 命中率 | >= 65% | 第一候选命中标注根因 |
| 根因 Top-3 命中率 | >= 85% | 前三候选包含标注根因 |
| 有效证据引用率 | >= 90% | 引用存在且支持对应陈述 |
| 无依据关键陈述率 | <= 5% | 无工具或文档证据支撑 |
| 只读工具成功率 | >= 95% | 排除测试中主动注入的后端故障 |
| 未审批变更阻断率 | 100% | 强制发布门禁 |
| 重复变更幂等阻断率 | 100% | 强制发布门禁 |
| 检查点恢复成功率 | 100% | 规定的恢复用例必须全部通过 |
| 调查 P95 时长 | <= 180 秒 | 在指定验收环境和模型下记录 |
| Trace 完整率 | >= 95% | 核心步骤存在同一关联 Trace |

成本不设脱离模型的固定金额门槛。验收报告必须记录模型版本、输入/输出 Token、中位数和 P95 单次成本，并保证候选版本不高于基线版本 10%，除非任务成功率有经评审确认的显著提升。

## 6. 项目成果目标

最终仓库至少应包含：

- 可通过 Docker Compose 一键运行的开发环境。
- Python、Go、TypeScript 三部分源代码及测试。
- Protobuf API 契约。
- 不少于 30 个版本化评测用例。
- 故障注入脚本和预期根因标签。
- 架构说明、威胁模型和关键 ADR。
- 自动化评测报告与性能/成本报告。
- 一段完整演示：注入故障、收到告警、调查、审批、处置、恢复验证和复盘。
