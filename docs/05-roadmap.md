# 阶段性任务

## 1. 总体节奏

建议用 10～12 周完成一个可公开演示的 V1。阶段按可验收成果划分，不以“写完某个模块”作为完成标准。每个阶段结束时都应有可运行软件、测试和文档。

当前进度（2026-09-02）：阶段 0 和阶段 1 已完成，阶段 2 尚未开始。API、订单、库存、支付和独立 PostgreSQL 组成五服务业务链路；OTLP Collector、Prometheus、Loki、Tempo、Grafana 和 cAdvisor 提供 Trace、Metric、Log 与容器资源证据。八类核心故障均已通过自动注入、证据断言和恢复验收。

## 2. 阶段 0：工程基线与需求冻结

预计时间：第 1 周。

### 任务

- 建立 `web`、`services/investigation`、`services/tool-gateway`、`proto`、`testbed`、`evals` 和 `deploy` 目录。
- 初始化 Python、Go、TypeScript 工程和统一开发命令。
- 配置 lint、类型检查、单元测试、依赖缓存和 CI。
- 编写领域术语表、错误分类和首批 ADR。
- 固定 V1 故障类型、成功指标和非目标。
- 定义模型适配器、Fake Model 和工具接口。

### 退出条件

- 三种语言的最小服务均能在 CI 构建和测试。
- Docker Compose 能启动空服务和 PostgreSQL。
- 所有密钥均通过环境变量或本地 Secret 文件注入。
- 本文档中的 V1 指标获得冻结版本号。

## 3. 阶段 1：可观测测试环境

预计时间：第 2 周。

### 任务

- 建立 5～8 个服务的测试业务链路，至少包含 API、订单、库存、支付模拟和数据库。
- 接入 OpenTelemetry SDK/Collector。
- 部署 Prometheus、Loki、Tempo 和 Grafana。
- 实现可重复故障注入：高延迟、错误率、CPU、内存、连接池、依赖不可用、配置错误和发布回归。
- 为每个故障定义 Ground Truth、影响范围和预期证据。

### 退出条件

- 一条请求可在指标、日志和 Trace 中关联。
- 至少 8 个核心故障能通过命令重复注入和恢复。
- 故障标签和时间窗口可被自动记录。

## 4. 阶段 2：Go 只读工具网关

预计时间：第 3～4 周。

### 任务

- 定义 Protobuf 工具协议和错误码。
- 实现身份传播、Deadline、限流、响应大小限制和审计中间件。
- 实现 Prometheus、Loki、Tempo、测试发布记录和 Git 只读连接器。
- 在 kind 环境实现 Kubernetes 状态与 Event 连接器。
- 编写 Fake Connector、契约测试和并发测试。
- 对日志、标签和工具结果做敏感信息脱敏。

### 退出条件

- 至少 8 个只读工具通过契约测试。
- Python 生成客户端可以调用网关并传播 Trace。
- 超时、权限失败、限流和数据源不可用具有稳定错误语义。
- 网关不接受任意 Shell、PromQL 之外的任意代码或动态工具注册。

## 5. 阶段 3：Python 调查工作流

预计时间：第 5～6 周。

### 任务

- 定义 Investigation、Evidence、Hypothesis 和 Action 领域模型。
- 实现告警接入、范围判定、证据收集、假设生成、验证和报告节点。
- 使用 LangGraph Postgres Checkpointer 保存状态。
- 实现调查预算、循环上限、取消和恢复。
- 实现模型适配层、结构化输出校验和一次修复策略。
- 为核心状态机实现 Fake Model 单元测试。

### 退出条件

- 使用 Fake Model 可确定性完成全流程。
- 使用真实模型可对至少 5 个故障输出带证据 Top-3 根因。
- 杀死并重启 Python 服务后调查能够继续。
- 任一证据源不可用不会导致整个调查无条件失败。

## 6. 阶段 4：知识检索与证据工作台

预计时间：第 7 周。

### 任务

- 建立 Runbook、服务说明和历史事故的导入流程。
- 实现关键词 + pgvector 混合检索和元数据过滤。
- 实现证据去重、裁剪、可靠性等级和引用校验。
- 开发调查列表、时间线、假设和证据详情页面。
- 通过 SSE 展示调查进度，支持断线重连。

### 退出条件

- 用户可以从结论跳转到对应查询和证据片段。
- RAG 具有独立 Recall@K 基线报告。
- 页面刷新或 SSE 断开不丢失调查结果。

## 7. 阶段 5：人在回路与隔离处置

预计时间：第 8 周。

### 任务

- 实现操作风险分级和审批状态机。
- 实现批准、修改、拒绝和过期。
- 在 Go 网关实现审批令牌、参数哈希、幂等和审计。
- 仅在隔离测试环境实现重启、扩缩容和回滚。
- 实现操作后 SLI 与告警恢复验证。
- 编写越权、重放、参数篡改和重复执行测试。

### 退出条件

- 未审批变更全部被拒绝。
- 审批后修改目标或参数会使令牌失效。
- 相同幂等键不会产生重复副作用。
- 每次变更都有执行前后证据和审计事件。

## 8. 阶段 6：评测与质量门禁

预计时间：第 9～10 周。

### 任务

- 将故障场景扩充到不少于 30 个用例。
- 实现工具响应录制、脱敏、冻结和离线回放。
- 实现根因排名、证据引用、安全、延迟和成本指标。
- 比较至少两个 Prompt 或模型配置。
- 建立失败分类：检索失败、工具失败、推理失败、引用失败、权限失败和预算失败。
- 将确定性测试和离线评测接入 CI。

### 退出条件

- 生成 JSON 与 Markdown 评测报告。
- 达到项目目标文档中的 V1 量化门槛。
- 安全强制用例失败时 CI 返回非零状态。
- 每个失败用例可定位到 Trace、检查点和工具记录。

## 9. 阶段 7：工程加固与发布演示

预计时间：第 11～12 周。

### 任务

- 完成并发、故障恢复、资源限制和安全测试。
- 补充架构图、威胁模型、API 文档、部署文档和 ADR。
- 固定可演示故障脚本和验收数据集版本。
- 输出性能、成本、准确率和失败案例报告。
- 录制完整产品演示。
- 清理密钥、敏感日志和不可复现依赖。

### 退出条件

- 新环境按照 README 可以完成部署、注入故障和验收。
- 所有 P0/P1 验收项通过。
- 演示包含失败或不确定案例，不只展示成功样例。
- 发布 Tag 绑定源码、数据集、Prompt、模型配置和评测报告。

## 10. 优先级规则

### P0：必须完成

- 告警到 RCA 的只读闭环。
- 证据引用。
- 状态恢复。
- 安全审批和阻断测试。
- 30 个故障用例与自动评测。
- 全链路可观测性。

### P1：应当完成

- 隔离环境中的重启、扩缩容和回滚。
- 混合检索和历史事故推荐。
- Web 调查时间线和评测报告页面。

### P2：有余力再做

- MCP 适配器。
- 多 Agent/子图实验。
- 语音或 IM 机器人入口。
- Temporal、Kafka、独立搜索集群。
- 多租户与企业 SSO。

P2 不得挤占 P0 的评测、安全和复现工作。
