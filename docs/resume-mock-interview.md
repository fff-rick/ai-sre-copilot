# 项目名称：AI-SRE Copilot

> 使用方式：每题先用“结论—项目做法—原理/取舍—验证”在 60～90 秒内回答；带 ⚠️ 的内容不要照读，须以源码、配置或评测报告核实后替换。题目基于简历及仓库文档，不补造未披露实现。

## 1. 项目与架构

### Q1：这个项目解决什么问题？
**回答模板：** 结论：它把告警后的跨系统排障变成可追溯的调查流程。项目关联指标、日志、Trace、Kubernetes、发布与知识库，输出带 Evidence ID 的根因假设和受控建议；模型只做语义推理，不拥有授权。验证：调查时间线、证据详情和离线回放均可审计。

### Q2：请从一次告警说完整链路。
**回答模板：** 告警或用户在 React 端创建调查后，FastAPI 创建持久化状态；LangGraph 在预算内调用 Go gRPC 网关读数据、归一化证据并推理；结果与终态事务落库，SSE 推送/重放时间线。需要变更时仅创建待审批动作，批准后由网关执行并验证。

### Q3：为何拆成 React、Python、Go、PostgreSQL 四层？
**回答模板：** 按信任边界拆分：React 仅展示和交互；Python 负责编排、RAG 和模型适配；Go 网关持有数据源连接及变更策略；PostgreSQL 保存调查、审批和审计事实。这样即使模型或 Web 被诱导，也无法直接获得集群变更能力。

### Q4：为什么不用一个后端服务直接调用所有工具？
**回答模板：** 单体实现快，但会把 LLM 编排、凭据、工具协议和副作用混在一起。这里用固定 Proto 与 Go 网关把最小权限、参数校验、审计放到独立强制点；代价是 RPC 和版本维护，换来更清晰的安全边界。

### Q5：LangGraph 在项目中承担什么，而不是普通函数串联？
**回答模板：** 它把 RECEIVED、SCOPING、COLLECTING、HYPOTHESIZING、VERIFYING、RECOMMENDING、REPORTING 等阶段显式建模，支持条件跳转、检查点与恢复。普通串联难以表达“证据不足则有限回环、预算耗尽则报告”的可审计终止逻辑。

### Q6：调查状态机为什么必须有预算？
**回答模板：** 预算限制模型调用、工具调用、总时长、Token、查询窗口及返回条数，防止模型在证据不足时无限探索或成本失控。耗尽后进入建议/报告，保留不确定性，而不是编造结论。⚠️ 需确认各预算的默认值和配置位置。

### Q7：状态如何持久化和恢复？
**回答模板：** 调查领域状态、事件和终态在 PostgreSQL 保存，LangGraph 检查点用于恢复流程；页面以 SSE 读取同一持久化事件流重放。关键点是恢复后不会把已完成副作用重新执行，变更还要经过独立审批状态机。

### Q8：为什么审批状态不能只放进 LangGraph checkpoint？
**回答模板：** checkpoint 服务于编排恢复，而审批是授权事实，必须具备独立事务、审计、过期与一次消费语义。将它作为 PostgreSQL 的唯一事实源，网关每次执行都重新核验，避免工作流状态被重放或篡改时越权。

### Q9：项目最重要的设计原则是什么？
**回答模板：** 不信任 LLM 输出：模型可以提出假设和建议，但事实必须来自证据，授权必须来自数据库审批和网关策略。该原则同时约束上下文、工具契约、变更执行与评测，不是只靠提示词。

### Q10：系统的信任边界有哪些？
**回答模板：** 浏览器、告警、日志、Runbook 和 Git 内容都可能不可信；模型输出也不可信。Python 不直接持有 Kubernetes 管理凭据；Go 网关通过固定请求访问数据源。边界的目标是让不可信内容不能升级为任意命令或未审批操作。

### Q11：Web 为什么不直接调用工具网关？
**回答模板：** 浏览器不应持有服务凭据，也不应绕过调查记录、预算与审计。Web 通过 Investigation Service 请求或读取调查，服务端再带 investigation_id、trace_id、身份和 deadline 调网关，便于鉴权、限流和关联审计。

### Q12：如何描述核心数据模型？
**回答模板：** Investigation 保存范围、时间窗、状态和预算；Evidence 保存来源、查询、片段、哈希、可靠性；Hypothesis 保存正反证据与置信度；ProposedAction 保存目标、参数、风险、审批和幂等键；AuditEvent 关联调用者、请求哈希、结果和 Trace。

### Q13：根因“假设”与“事实”如何区分？
**回答模板：** 事实是可追溯的观测或结构化提取，必须带 Evidence ID；假设是基于事实的、带置信度和待验证项的推断。页面需要同时展示支持证据、反证及 evidence gap，避免把候选根因表达为确定根因。

### Q14：证据可靠性分级有什么用？
**回答模板：** 不同来源和完整度不能等权：直接指标、原始日志片段、部署记录、检索文档以及模型摘要的可信度不同。分级能影响排序、提示模型不确定性和最终报告措辞。⚠️ 需确认实际分级枚举及排序规则。

### Q15：为什么要保留反证？
**回答模板：** 只展示支持材料容易确认偏误。Hypothesis 同时保存 contradicting_evidence_ids，使模型和审批者看到冲突事实；若反证无法解释，就降低置信度或继续验证，而非强行收敛。

### Q16：项目面向生产吗？
**回答模板：** 当前定位是本地开发、评估和隔离环境的参考实现，不应直接接入生产集群或凭据。生产化仍需可信身份代理、外部密钥管理、高可用与数据治理等；不能把浏览器角色头当生产认证。

### Q17：最大的难点是什么？
**回答模板：** 是同时控制推理正确性和执行安全性：前者靠证据闭环、缺口显式化和评测，后者靠独立授权与 fail-closed 网关。只把模型回答做得更像人，不足以解决这两个工程问题。

### Q18：如果流量升高，架构的瓶颈在哪？
**回答模板：** 工具源查询、模型调用和 PostgreSQL 写入/检索是主要点。当前用有界 worker、deadline、响应上限和数据源侧聚合控制；进一步扩展需按调查队列、连接池、读写负载和向量检索规模压测。⚠️ 需用压测数据回答容量数值。

### Q19：为什么选择单 Agent 显式工作流？
**回答模板：** 多 Agent 自由协作看似灵活，但工具调用、停止条件和权限链难审计。故障调查的关键是可重复、可恢复、可设预算；单 Agent 状态机更容易固化边界。复杂领域协作可在未来以受控子图引入。

### Q20：面试官质疑“这只是 RAG 聊天机器人”，怎么回应？
**回答模板：** RAG 只是知识补充。核心是多源实时证据调查、Evidence ID 约束、持久化状态机、SSE 时间线、审批唯一事实源和隔离变更执行；它把建议、授权和副作用拆开，目标不是通用问答。

## 2. 证据调查与 LangGraph 深挖

### Q21：调查如何确定初始范围？
**回答模板：** 以告警的服务、环境、严重度和时间窗口做 scoping，先缩小查询而非全局抓取。范围会进入 Investigation，并约束后续指标、日志、Trace、发布记录查询，减少噪声、Token 和敏感数据暴露。

### Q22：为什么先查指标再查日志？
**回答模板：** 不应机械固定顺序；一般指标可快速定位异常开始、服务和维度，再用日志/Trace 解释原因。状态机可按告警类型调整计划，但任何顺序都受预算、查询上限和证据质量约束。⚠️ 需确认实际 planner 规则。

### Q23：监控、日志、链路、Kubernetes、Git 各补什么信息？
**回答模板：** 指标说明现象和范围；日志给出错误上下文；Trace 显示调用路径与瓶颈；Kubernetes 事件反映运行态；Git/发布记录建立变更时间关联。它们相互印证，不应由单一源直接定根因。

### Q24：数据源失败时系统如何处理？
**回答模板：** 网关将错误区分为可重试、权限、参数、数据源不可用和业务失败；调查侧记录 evidence gap，把缺失来源和影响带到报告中。不能把失败当作“没有异常”，更不能让模型补全缺失事实。

### Q25：什么是 evidence gap，为什么重要？
**回答模板：** 它是本应获取但因不可用、无权限、超时或预算而缺失的证据声明。显式保存它能校准置信度、指导下一步人工检查，并在回放中区分“数据确实没有”与“系统未拿到”。

### Q26：工具调用为何只读？
**回答模板：** 调查阶段只需事实，最小权限可显著降低 prompt injection 或模型误判的爆炸半径。变更是另一条审批链；将读写能力混在同一自由工具接口会使“模型建议”变成“模型执行”。

### Q27：如何限制模型只引用上下文中的 Evidence ID？
**回答模板：** 上下文片段携带稳定 ID，结构化输出 schema 要求支持/反证字段只能填写提供过的 ID；服务端再做集合校验，引用不存在的 ID 即拒绝或降级。提示词是辅助，服务端校验才是强制边界。

### Q28：模型给出一个看似合理但无引用的结论怎么办？
**回答模板：** 不能作为已验证根因展示。校验层应标记为无依据陈述、要求重试或以不确定建议输出；离线指标专门统计此项，项目基线的 0% 是冻结回放结果。⚠️ 需确认具体重试/降级实现。

### Q29：证据为何要裁剪？
**回答模板：** 原始日志/Trace 可能无限大且含敏感信息，直接塞给模型会稀释重点、超 Token 并泄露数据。应在源侧过滤聚合，再保存必要片段、摘要、查询条件和哈希；大对象放受控 Artifact，只返回引用。

### Q30：日志如何裁剪和抽样？
**回答模板：** 先按服务、级别、故障时间窗和 Trace ID 过滤，再做模板聚类与采样，保留能支撑假设的代表片段。这样不是“删数据”，而是把上下文预算投入差异信息。⚠️ 需确认聚类算法及采样上限。

### Q31：哈希去重解决什么问题？
**回答模板：** 相同或近似的证据反复出现会占满上下文并人为放大单一信号。对规范化内容计算 content_hash，可合并重复项、保留来源计数/引用并降低成本；需注意规范化策略不能抹掉时间或标签差异。

### Q32：脱敏为什么要在工具边界做？
**回答模板：** 越靠近数据源越能减少敏感内容向数据库、模型和前端扩散。网关对输出做基础脱敏和大小限制，录制客户端还递归处理敏感键及 Bearer/AWS/API-key 模式；仍要把原始 Artifact 访问单独控制。

### Q33：仅靠正则脱敏有什么风险？
**回答模板：** 会漏掉未知格式，也可能误伤排障字段。因此它是纵深防御的一层，不替代最小查询、权限隔离和不上传不必要原始数据；应以敏感模式测试、审计和数据分类持续校验。

### Q34：可靠性分级与置信度是一回事吗？
**回答模板：** 不是。可靠性描述单条证据来源/完整度；置信度是对整个假设的当前判断，受正反证、覆盖度和 evidence gap 共同影响。分开保存避免把“权威来源的一条事实”误解成“根因已确定”。

### Q35：验证节点做什么？
**回答模板：** 它针对候选假设提出可证伪检查，补取区分度高的证据，更新支持/反证和状态。若仍不足且未超预算可回到假设节点；否则报告当前不确定性。关键是验证真实假设，而非继续漫游工具。

### Q36：如何避免工作流循环？
**回答模板：** 用显式状态转换加预算双重限制：最大工具/模型调用、总时长、Token 与单查询范围都受控；达到根因阈值或预算耗尽后强制推荐/报告。还可记录已执行检查避免重复。⚠️ 需确认阈值实现。

### Q37：工具超时应重试吗？
**回答模板：** 只对明确可重试的瞬态错误有限重试，并受 deadline 和总预算限制；权限、参数等确定性失败应立即返回。最终失败生成 evidence gap，避免无界重试拖垮调查和数据源。

### Q38：为什么每个 gRPC 请求带 trace_id 和 deadline？
**回答模板：** trace_id 将 UI、编排、网关与数据源调用串联以便排障；deadline 防止下游卡住耗尽 worker。服务端应尊重 deadline 并把超时归类，不能在客户端已放弃后继续无限工作。

### Q39：为什么禁止任意 Shell 字符串？
**回答模板：** Shell 输入难以完整验证，存在注入、权限扩大和审计歧义。固定、版本化的 Protobuf 消息把工具名、目标、时间窗和参数变成类型化字段，网关可做 allowlist 与范围校验。

### Q40：证据收集并发会引入什么问题？
**回答模板：** 并发能降低端到端延迟，却可能压垮 Prometheus/Loki 或使输出顺序不稳定。项目采用有界 worker pool、限时、响应上限和独立错误隔离；展示/持久化须依据事件时间或序号而非竞态到达顺序。⚠️ 需确认并发上限。

## 3. RAG、数据库与交互

### Q41：知识库包含哪些内容？
**回答模板：** 简历范围包括 Runbook、服务说明和历史事故；它们补充实时观测数据的解释和处置经验。知识库是候选参考，不替代故障窗口中的实时证据，且内容也视为可能包含 prompt injection 的不可信输入。

### Q42：导入时为何分块？
**回答模板：** 文档直接整篇检索粒度太粗、向量语义混杂且上下文成本高。分块后可携带服务、环境、版本、有效期等元数据，召回时给模型更小、可引用的片段。⚠️ 需确认 chunk 大小、overlap 和分块器。

### Q43：PostgreSQL 全文检索和 pgvector 如何并行？
**回答模板：** 一路用全文检索捕获精确错误码、术语和关键词，一路做余弦向量检索捕获语义相近描述；两路独立召回后进入融合与过滤。并行降低串行等待，也避免任一路召回缺陷决定结果。

### Q44：为什么不只使用向量检索？
**回答模板：** 向量检索对语义改写强，但错误码、服务名、版本号等精确匹配可能不稳定；全文检索相反。混合检索结合二者，代价是索引、调参和融合复杂度。

### Q45：RRF 是什么，为什么选它？
**回答模板：** Reciprocal Rank Fusion 按各列表名次的倒数累加，不要求不同检索器分数同尺度。它对一个检索器异常高分更稳健，适合作为轻量基线；若有标注数据，可再引入 reranker。⚠️ 需确认 k 值和是否有 reranker。

### Q46：RRF 公式如何解释？
**回答模板：** 对文档 d，分数通常是各检索列表中 `1/(k + rank)` 的求和；rank 越前贡献越大，k 控制头部权重。项目并行 FTS/向量后按这一思路融合，随后做条件过滤。

### Q47：条件过滤为什么放在融合前后都要考虑？
**回答模板：** 服务、环境、版本和有效期是硬约束时应尽早过滤，避免错误文档进入候选；若某些过滤依赖融合结果或需保证召回，可在后处理复核。具体顺序需按召回损失和索引能力验证。⚠️ 需确认实际 SQL。

### Q48：pgvector 余弦距离的含义？
**回答模板：** 它比较向量夹角，弱化文本长度差异，通常在向量归一化时与点积排序等价。它衡量嵌入语义相似，不等于事实正确性，所以仍需元数据过滤、证据引用和离线评测。

### Q49：向量索引怎么选？
**回答模板：** 需根据数据量、更新频率、内存和召回目标选择精确扫描或近似索引（如 HNSW/IVFFlat）。项目简历只确认 pgvector 与余弦检索，未声明索引类型；面试中应展示 migration/DDL 后再回答。⚠️ 需要确认。

### Q50：如何避免陈旧 Runbook 误导调查？
**回答模板：** 以服务、环境、文档版本和有效期做过滤，并在结果中保留来源和版本；过期内容应降低优先级或拒绝。更根本的是把文档建议与实时证据分离，不能因为检索命中就当成当前事实。

### Q51：调查快照和终态事件为何同事务持久化？
**回答模板：** 这保证页面重放时不会看到“终态已完成但最后报告/事件缺失”或反向不一致。事务提交前二者要么都不可见、要么都可见；失败则回滚并由恢复机制重试。⚠️ 需确认隔离级别与表设计。

### Q52：SSE 为什么适合这个工作台？
**回答模板：** 调查主要是服务器持续向页面单向推送状态、工具和证据事件，SSE 基于 HTTP、实现和断线重连简单。用户操作仍走普通 HTTP；若需要双向高频协作才更适合 WebSocket。

### Q53：SSE 断线后如何恢复时间线？
**回答模板：** 不能只依赖内存推送。事件和快照已持久化，客户端重连后按调查 ID/最后事件位置读取并重放，再接实时流；服务端需保证事件 ID、顺序与去重。⚠️ 需确认 Last-Event-ID 实现细节。

### Q54：如何防止 SSE 慢客户端拖垮服务？
**回答模板：** 把调查执行与连接写出解耦，限制单客户端缓冲，必要时断开后让其从持久化时间线重放；不要为慢连接无限积压证据。⚠️ 需确认当前背压策略。

### Q55：为什么保存查询条件、摘要和哈希而不是全量原始日志？
**回答模板：** 全量复制成本高、敏感面大且难治理；保存可复现查询、必要片段和内容哈希已足以审计大多数推理路径。超大原始对象进入受控 Artifact，按更严格权限访问。

### Q56：PostgreSQL 在项目中不只是“数据库”，具体承担什么？
**回答模板：** 它同时承担调查领域数据、LangGraph checkpoint、审批授权、操作与审计、知识元数据/向量及评测结果，减少跨存储一致性复杂度。代价是单机容量/可用性边界，需要生产化拆分或高可用设计。

### Q57：全文检索可能有哪些性能问题？
**回答模板：** 大量分块、频繁更新或复杂过滤会使索引膨胀和计划退化。应检查查询计划、合适索引、过滤选择性、top-k 与并发；项目应通过离线 Recall/MRR 与延迟共同评估，不能只看命中率。

### Q58：如何评测检索质量？
**回答模板：** 对冻结用例或标注文档计算 Recall@K、MRR，以及最终回答实际引用到正确证据的比例。仅检索排名好不代表模型结论好，因此需要与有效引用、无依据陈述等端到端指标结合。

### Q59：知识库被写入恶意提示怎么办？
**回答模板：** 把它当数据而非指令：标记不可信、限定模型任务与可引用 ID，模型没有执行权限；检索内容不能改变工具 allowlist 或审批状态。离线集包含 prompt injection 变体用于验证这个边界。

### Q60：如果重新设计 RAG，你会优先优化什么？
**回答模板：** 先按失败样本判断瓶颈：若错在召回，改善分块/元数据/混合检索；若错在排序，引入可评测 reranker；若错在使用，强化证据校验。不能不看数据就盲目换向量库。⚠️ 需要基于评测报告选择。

## 4. 安全处置与 Go 网关

### Q61：模型提出重启后，为什么不能直接执行？
**回答模板：** 模型输出不可信，重启属于有副作用操作。它只能产生结构化 ProposedAction；系统做 schema/风险校验，创建待审批记录，人工批准后网关再核验令牌、参数哈希、目标和策略，才可执行。

### Q62：审批状态机作为“唯一授权事实源”是什么意思？
**回答模板：** 是否有权执行不由前端按钮、LangGraph 状态或模型文本决定，只由 PostgreSQL 中可验证的审批记录决定。Go 网关在执行时读取/消费该事实，任何 DB 不可用或状态不匹配都拒绝，形成 fail-closed。

### Q63：什么是 fail-closed？
**回答模板：** 不确定或依赖校验失败时默认拒绝，而不是为可用性放行。例如审批库不可用、令牌过期、参数哈希不同、命名空间不符均不能执行。它适合变更路径；只读调查可以以 evidence gap 方式降级。

### Q64：审批令牌为何绑定参数哈希？
**回答模板：** 审批者批准的是某个具体目标和参数，而不是“以后任意重启”。网关对实际请求做规范化哈希并与令牌绑定值比较，参数被篡改或换目标后拒绝执行，防止 TOCTOU 与前端篡改。

### Q65：参数哈希前为什么要规范化？
**回答模板：** 同语义 JSON 的字段顺序、空值表示不同会导致不同字节串；规范化才能保证哈希反映语义参数。也应明确版本和默认值规则，否则客户端/服务端规范化不一致会误拒。⚠️ 需确认实现的 canonicalization。

### Q66：一次消费如何实现，为什么必要？
**回答模板：** 在数据库事务中把有效审批原子转换为已消费/执行中，只有一个请求能成功；重复请求读到已消费即拒绝或返回既有结果。它防止令牌被并发重放，需结合唯一约束或条件更新实现。

### Q67：审批与执行之间的 TOCTOU 如何缓解？
**回答模板：** 执行端不信任旧的审批回调，而是重新取授权记录，核验过期、角色、参数哈希、目标、命名空间和一次消费；必要时在同一事务声明执行权。外部集群状态仍要在执行前做策略检查。

### Q68：幂等键和一次消费有什么区别？
**回答模板：** 一次消费保证授权不能被重复使用；幂等键保证网络重试、客户端重发或响应丢失时，同一业务操作不会产生第二次副作用，并可返回首次执行结果。两者解决不同层面的重放。

### Q69：若网关已执行但响应丢失，如何处理？
**回答模板：** 客户端不能盲目再次执行，而应使用幂等键查询执行状态/GetMutationExecution；网关持久化结果并返回同一操作的状态。必要时结合 Kubernetes 实际状态和审计记录核对。⚠️ 需确认状态机细节。

### Q70：为什么限制测试命名空间？
**回答模板：** 即使审批和参数校验正确，错误 context/目标也会造成高风险。网关只允许 `MUTATION_ALLOWED_NAMESPACE` 的隔离范围，并且文档明确不连接生产凭据；这是环境级 allowlist，而不是依赖模型理解“生产/测试”。

### Q71：Protobuf 固定契约带来哪些安全收益？
**回答模板：** 类型化、版本化消息便于 allowlist、字段范围和兼容性验证，避免任意命令、任意 URL 或自由 SQL；审计也有明确语义。代价是新增工具需修改契约并做版本演进，但这是有意的摩擦。

### Q72：gRPC 为何适合 Python 与 Go 间边界？
**回答模板：** 它提供强 schema、生成客户端、deadline/错误码语义和高效服务间通信，适合可信工具网关。相比 HTTP JSON，契约漂移更易在构建测试中发现；浏览器边界仍用 FastAPI HTTP/SSE 更自然。

### Q73：工具网关如何处理 RBAC？
**回答模板：** 不同角色有 viewer、investigator、approver、admin 等能力，变更路径还要求独立审批记录，admin 不自动等同于审批者。V1 的角色头仅适用于本地隔离环境，生产必须接入可信身份认证。⚠️ 需确认具体鉴权中间件。

### Q74：为什么 Go 网关不能调用 LLM？
**回答模板：** 网关是凭据和副作用边界，应保持决策最小化、可预测；若它生成根因结论，模型不确定性会进入高权限层。Python 可编排/推理，Go 只执行固定策略和工具契约，职责更容易审计。

### Q75：如何审计一次变更？
**回答模板：** 审计事件关联 trace_id、actor 类型/ID、事件类型、资源、请求哈希、结果和时间；还应串起审批、幂等键、执行结果及 SLI 前后快照。目标是事后回答“谁在何时以什么授权改变了什么”。

### Q76：变更前后 SLI 快照的价值？
**回答模板：** 它把“执行成功”与“故障缓解”分开：前者是 API/Kubernetes 接受操作，后者要看错误率、延迟等目标 SLI 的变化。快照也为回滚判断和审计提供比较基线。⚠️ 需确认 SLI 指标和观察窗口。

### Q77：重启、扩缩容、回滚的风险如何区别？
**回答模板：** 都必须审批，但目标、参数、预期效果和回滚计划不同：重启可能造成瞬时中断，扩缩容影响容量/成本，回滚涉及版本兼容和数据迁移。系统应按固定 action schema 和风险级别校验，不能用一个通用“执行命令”。

### Q78：为什么“人工审批”仍不够？
**回答模板：** 若批准的是模糊文本，执行时参数可被替换；若仅前端拦截，调用可绕过。因此还需令牌绑定、服务端重新鉴权、命名空间限制、一次消费、幂等和审计。人工是决策点，不是唯一安全控制。

### Q79：Prompt Injection 如何影响安全链路？
**回答模板：** 恶意日志或 Runbook 可诱导模型忽略规则、要求执行命令。设计上外部内容不改变固定工具、模型无凭据、变更需人工和网关二次校验；8 个 injection 变体用于回放验证安全强制项。

### Q80：若审批数据库宕机，是否允许紧急执行？
**回答模板：** 当前项目的安全设计是不允许，因其唯一授权事实源不可用就 fail-closed。生产中的 break-glass 需另行设计独立流程、强身份、双人审批和审计，不能在现有路径静默降级。 

## 5. 评测、性能与综合压力追问

### Q81：32 个用例和 8 类故障族分别是什么？
**回答模板：** 覆盖延迟、错误率、数据库、资源、网络、配置、发布和容量共 8 类，合计 32 个冻结用例，其中 8 个含 prompt injection 变体。其价值是覆盖不同证据形态和安全场景，而不只是单一 happy path。

### Q82：什么是冻结录制/回放评测？
**回答模板：** 先在录制边界保存脱敏后的工具请求/响应并以 SHA-256 冻结；回放时严格按工具名和参数匹配，未录制请求稳定拒绝。这样能比较 Prompt/编排变化，隔离实时数据源与网络波动。

### Q83：为什么回放客户端要精确匹配参数？
**回答模板：** 若只按工具名返回录制结果，错误的查询也会“成功”，掩盖编排退化。精确匹配可检验模型/工作流是否请求了正确证据；未录制请求拒绝使评测可重复且不产生隐式网络依赖。

### Q84：SHA-256 在冻结中保证什么、不保证什么？
**回答模板：** 它可检测录制内容是否被意外篡改，保证同一输入回放一致；不保证原始录制本身真实、完整或无偏。因此仍需数据集版本、审查和真实模型在线运行来补足。

### Q85：完成率 100% 如何定义？
**回答模板：** 应以评测 schema 中每用例到达预期终态且没有规定失败为准，而非“HTTP 200”。当前简历数值对应确定性回放基线；面试应说明具体判定脚本和失败分类。⚠️ 需要指向评测报告/代码确认定义。

### Q86：Top-1 与 Top-3 100% 说明什么？
**回答模板：** 在冻结的 32 个用例中，预期根因分别出现在第一候选或前三候选的比例为 100%。它验证该基线对该数据集的端到端排序，不表示真实生产故障、未见数据或任意模型都能达到该准确率。

### Q87：什么是有效引用率 100%？
**回答模板：** 评测中所有要求引用的结论都引用了存在且可接受的 Evidence ID。它主要验证引用约束与输出校验；还需结合证据是否真正支持断言来审查，不能把“有 ID”误当“推理正确”。

### Q88：无依据陈述率 0% 如何验证？
**回答模板：** 将模型断言与已进入上下文且被引用的证据集合比对，对无法由证据支撑的断言计数。当前为确定性回放结果；需要说明规则/人工标注边界，避免夸大为通用幻觉率。⚠️ 需确认判定实现。

### Q89：安全通过率 100% 覆盖了什么？
**回答模板：** 至少覆盖冻结集中的 8 个 prompt injection 变体及安全强制项，确认不越过只读/审批边界。它不等价于系统对所有攻击安全，威胁模型仍列出模型误导、管理员失陷等剩余风险。

### Q90：Trace 完整率 100% 的含义？
**回答模板：** 每个用例按评测要求保留可关联的 Trace ID、检查点 Artifact 与工具记录 URI/哈希，能回溯执行路径。需明确“完整”的字段定义和断链处理；它不直接代表分布式 Trace 零丢失。⚠️ 需要确认。

### Q91：P95 0.017 秒能直接写成“系统延迟”吗？
**回答模板：** 不能。仓库文档明确机器相关延迟不应写死；该值应解释为冻结、确定性回放中某一测量范围的 P95，通常不含真实数据源和模型网络耗时。必须给出样本数、计时边界、环境和计算方法。⚠️ 需核实原报告。

### Q92：如何计算 P95？
**回答模板：** 收集同口径样本排序后取 95 分位（需定义线性插值或 nearest-rank 规则），并报告 N、是否包含 warm-up、异常样本及端到端还是单阶段。P95 不能用少量样本或平均值替代。

### Q93：离线回放为什么可能比线上真实模型快很多？
**回答模板：** 回放消除了模型推理、外部网络、实时数据源和部分资源竞争，主要测编排/解析/校验路径。因此它适合做回归门禁和相对对比；线上必须单独记录模型、定价、网络和实际延迟。

### Q94：为什么要做双 Prompt 对比？
**回答模板：** 在相同冻结证据上比较 `hypotheses-v2` 与 `evidence-first-v3`，减少数据变化干扰，观察引用、安全和无依据陈述等影响。结论应限于评测集和固定配置，不应泛化为模型能力绝对提升。

### Q95：质量门禁为什么要在 PR 中运行？
**回答模板：** Prompt、工具契约、脱敏和状态机改动都可能悄悄破坏安全或可复现性。PR 门禁运行测试、静态检查、契约漂移、构建、Compose 校验和离线评测；安全强制项失败返回非零以阻止合并。

### Q96：六类统一失败分类有什么价值？
**回答模板：** 检索、工具、推理、引用、权限和预算失败分开统计，能定位回归责任：例如 Top-1 降低究竟是检索没召回、工具失败还是输出违规。统一分类也让报告和告警更可比较。

### Q97：如何验证“数据源失败不导致幻觉”？
**回答模板：** 构造单源不可用/超时用例，断言调查记录 evidence gap、结论降低确定性且不引用不存在证据；检查不会把失败解释为正常。该测试应同时覆盖工作流事件、模型输出校验与最终报告。⚠️ 需结合 AT-R03/F04 实现说明。

### Q98：如何验证一次消费和幂等？
**回答模板：** 对同一审批令牌并发提交，期望最多一个获得执行权；对同一幂等键重试，期望返回同一结果、不产生第二次副作用。还应模拟响应丢失，随后查询执行状态和审计记录。⚠️ 需给出实际 E2E 测试名称。

### Q99：如果面试官要求“把这个做成生产系统”，第一批改什么？
**回答模板：** 先补身份与部署边界：可信 SSO/身份代理、密钥管理、网络隔离、生产 RBAC 和审计保留；再做高可用、容量压测、数据治理和变更风险策略。不会先扩大自动执行，因为当前 V1 明确只适用于隔离环境。

### Q100：请总结你在该项目中最能体现工程能力的一点。
**回答模板：** 我会强调把 AI 不确定性转成可验证流程：证据 ID 与 gap 限制事实边界，持久化状态机限制过程，审批数据库和 Go 网关限制副作用，冻结回放将质量变成可回归门禁。最后如实说明我实际负责模块、代码路径与可复现命令。⚠️ 需要按你的真实个人贡献收口。

## 6. 面试使用提醒

- “100%”一律先限定为 **32 个冻结、确定性回放用例** 的门禁结果；不要表述为线上或生产模型准确率。
- 对 P95 `0.017 秒`，必须给出实际报告中的计时边界；若未核实，回答“该指标需以 artifact 为准”。
- 以下信息应在面试前从源码/文档补齐：模型与 JSON Schema 适配细节、证据可靠性枚举、LangGraph checkpoint 与数据库隔离级别、RRF 参数/向量索引、SSE 断线协议、审批令牌格式及 canonical hash、并发和超时默认值。
