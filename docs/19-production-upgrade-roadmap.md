## 1. 升级结论

生产化采用“纵向打通一个窄场景，再横向扩展”的策略：

1. 首个生产切入点是**告警分诊 + 只读故障调查 + 变更关联**，先以影子模式运行，再进入人机协同。
2. 首期只选择一个业务团队、一个生产环境、2～5 个 Kubernetes 服务，以及 HTTP 错误率/延迟类 SLI 告警。
3. 首期故障族只覆盖**发布回归**和**下游依赖异常**；资源饱和在数据质量稳定后加入。
4. 首期只接入 Prometheus、Loki、Tempo、Kubernetes 只读接口、发布平台和代码仓库 API，不接任意 Shell、任意 SQL 或动态工具。
5. 生产变更不进入首期。重启、扩缩容和回滚只有在只读阶段达到质量、安全和运营门槛后，才进入限定工作负载的人工审批试点。
6. 身份、权限、审计、数据治理、高可用、备份恢复、可观测性和发布治理是所有场景的共同底座，必须先于生产数据接入完成。

### 1.1 首个生产试点边界

| 维度 | 纳入首期 | 首期不纳入 |
| --- | --- | --- |
| 用户 | 单个内部 SRE/研发值班团队 | 外部客户、自助多租户 |
| 环境 | 一个生产环境，只读访问 | 多集群统一控制面、跨云 |
| 服务 | 2～5 个已有明确 Owner 和 SLO 的 Kubernetes 服务 | 数据库、中间件、网络设备、虚拟机全覆盖 |
| 告警 | HTTP 错误率、延迟、可用性告警 | 安全告警、成本告警、容量预测 |
| 故障族 | 发布回归、下游依赖异常 | 数据正确性、复杂网络、未知安全事件 |
| 数据源 | 指标、日志、Trace、Kubernetes 状态、发布记录、Git 元数据 | 工单、CMDB 全量替换、云平台全部产品 |
| 系统行为 | 生成带证据的分诊、假设和下一步检查建议 | 自动静默告警、自动关闭事故、自动生产变更 |

首期成功不是“系统能回答所有问题”，而是它在上述边界内持续提供可信证据，能明确表达不确定，并能被值班团队安全地关闭或绕过。

## 2. 当前基线与生产差距

### 2.1 已具备的可复用能力

- Python 调查服务已经具备有界工作流、PostgreSQL 检查点、租约式 worker、取消和失败降级。
- Go 工具网关已经具备固定 gRPC 契约、参数校验、Deadline、限流、响应大小限制、基础脱敏和变更幂等控制。
- Web 已具备调查列表、时间线、SSE 重连、证据查看、质量报告和隔离环境审批交互。
- pgvector 混合检索、冻结评测集、离线回放、故障测试床和发布来源绑定可继续作为回归基础。
- 未审批、过期、参数篡改、重放和越权变更已有确定性安全测试。

### 2.2 必须正视的差距

| 领域 | 当前实现 | 生产缺口 | 代码或文档依据 |

| 部署 | 单机 Compose、本地卷、固定资源上限 | Kubernetes/平台化部署、多副本、滚动升级、PDB、NetworkPolicy、HPA、跨故障域数据库 | [Compose](../compose.yaml)、[部署手册](16-api-and-deployment.md) |
| 数据治理 | 有基础键名/Bearer 脱敏和长度限制 | 数据分类、字段级策略、租户隔离、模型出站控制、留存、删除和审计取证 | [威胁模型](15-threat-model.md)、[网关安全实现](../services/tool-gateway/internal/gateway/security.go) |
| 质量证明 | 32 个冻结用例主要来自可控测试床，回放模型用于确定性门禁 | 脱敏真实事故集、场景分层指标、人工复核一致性、线上漂移与反馈闭环 | [评测说明](../evals/README.md)、[阶段 7 验收](17-stage7-validation.md) |

结论：现有 V1 适合作为生产化内核，但身份、数据、运行和调查策略仍是演示级边界。任何生产试点都必须保留“AI 不持有高权限凭据、外部内容不可信、变更单独授权、失败时保守降级”四条原则。

## 3. 场景分类与优先级

场景按事故生命周期分类，故障族作为每个场景下的第二维度。这样可以避免按工具建设功能孤岛，也避免一开始承诺覆盖所有故障。

### 3.1 运维场景分类

| 编号 | 场景 | 用户要完成的工作 | 首期优先级 | 首期自治等级 |
| --- | --- | --- | --- | --- |
| SC-01 | 告警接入、去重与分诊 | 判断告警是否有效、影响谁、应由谁响应 | P0 | L1 影子，达标后 L2 辅助 |
| SC-02 | 多源故障调查与根因假设 | 形成时间、收集证据、提出并验证候选根因 | P0 | L1 影子，达标后 L2 辅助 |
| SC-03 | 变更关联与回退建议 | 判断故障是否与发布、配置或代码变更相关 | P0 | L2 辅助，只提供建议 |
| SC-04 | 恢复验证与事故收口 | 判断服务是否恢复、是否存在残余风险 | P1 | L2 辅助 |
| SC-05 | 事故知识与复盘 | 生成复盘草稿、沉淀有效证据和 Runbook 改进项 | P1 | L2 辅助，人工发布知识 |
| SC-06 | 审批式低风险处置 | 在严格策略内重启、扩缩容或回滚 | P2 | 初期 L2 建议，后期 L3 审批执行 |
| SC-07 | 主动可靠性分析 | 容量、性能、趋势、弱信号和日常巡检 | P3 | 暂不启动 |

P0/P1/P2/P3 表示进入路线的先后顺序，不代表业务价值高低。SC-06 风险最高，因此即使已有隔离环境实现，也必须排在只读能力稳定之后。

### 3.2 自治成熟度

| 等级 | 名称 | 系统权限 | 人的责任 | 允许上线条件 |
| --- | --- | --- | --- | --- |
| L0 | 离线评测 | 只读冻结数据 | 评审结果 | 数据集和门禁可复现 |
| L1 | 影子运行 | 读取生产副本或生产只读数据，不影响值班决策 | 正常按原流程处置，并标注对照结果 | 安全底座完成，生产数据授权完成 |
| L2 | 人机协同 | 输出分诊、调查和处置建议，不改变外部状态 | 人工确认、执行、关闭事故 | 影子指标达标且用户可随时绕过 |
| L3 | 审批执行 | 仅执行白名单动作，参数和目标被策略及审批绑定 | 独立审批者批准，系统验证效果 | 演练通过、可回滚、审计完整 |
| L4 | 条件自治 | 在极窄、确定性策略内自动执行 | 事后复核和随时熔断 | 至少两个版本周期稳定，另行立项 |

本路线只承诺推进到 L3。L4 不因“模型准确率高”自动开启，必须有可证明的确定性策略、故障预算和独立安全评审。

### 3.3 故障族分层

| 波次 | 故障族 | 典型证据 | 纳入条件 |
| --- | --- | --- | --- |
| F1 | 发布回归 | 发布事件、Commit、错误率/延迟拐点、版本维度日志和 Trace | 首期必做；目标服务必须有可靠发布元数据 |
| F2 | 下游依赖异常 | 依赖 Trace、客户端错误、超时、依赖 SLI、拓扑 | 首期必做；服务拓扑和 Trace 覆盖率达标 |
| F3 | CPU/内存/连接池等资源饱和 | 资源指标、限流/排队、Pod 状态、运行时日志 | 第二波；统一资源指标和基线完成后加入 |
| F4 | 配置错误 | 配置版本、Feature Flag、审计事件、实例差异 | 第二波；配置平台能提供可信变更事件后加入 |
| F5 | 数据库/消息系统 | 慢查询、锁、连接、消费滞后、拓扑 | 后续专项；只能通过固定只读查询，不开放任意 SQL |
| F6 | 网络/DNS/证书 | 网络遥测、DNS、证书事件、跨区指标 | 后续专项；需要网络团队和独立数据策略 |
| F7 | 数据正确性/业务异常 | 业务对账、数据质量规则、领域事件 | 后续专项；不能仅依赖 LLM 判断 |
| F8 | 安全事件 | SIEM、身份、审计、威胁情报 | 不复用普通故障流程直接上线，须单独威胁模型和团队授权 |

扩展规则：先增加同一故障族的服务覆盖，再增加新故障族；只有当前波次连续两个评测周期达标，才进入下一波次。

## 4. 各场景的阶段性开发任务与目标

### 4.1 SC-01：告警接入、去重与分诊

#### A. 生产接入准备

开发任务：

- 定义版本化 `AlertEvent` 契约，区分 firing、updated、resolved、reopened。
- 为首个告警源实现签名验证、时间戳防重放、事件幂等键和来源 allowlist。
- 建立 `alert -> incident -> investigation` 映射，按指纹、服务、环境和时间窗聚合重复告警。
- 接入最小服务目录：服务 Owner、环境、命名空间、Tier、SLO、Runbook、仪表盘和依赖。
- 增加告警风暴配额、最大并发调查数、排队和拒绝策略。
- 将 AI 判断与确定性事实分开：严重度、Owner、告警状态优先来自规则和服务目录。

阶段目标：生产告警可安全、幂等地进入系统，同一事件不会重复创建调查，错误映射可人工修正。

退出条件：

- 重放、伪造签名和过期 Webhook 100% 被拒绝。
- 同一告警事件并发投递 100 次只创建一个逻辑事件。
- 首期服务的 Owner、环境和 SLO 映射完整率为 100%。
- 告警风暴不会突破配置的调查并发和模型预算。

#### B. L1 影子分诊

开发任务：

- 在不改变现有通知和升级链路的条件下生成影响范围、责任团队和优先级建议。
- 保存人工实际分诊结果，建立一致/部分一致/错误/信息不足标签。
- 展示输入缺失、映射失败和数据源降级，不对值班人员隐藏失败。
- 记录分诊耗时、人工修正率和重复告警压缩率。

阶段目标：证明分诊建议有用，但不让系统承担生产决策责任。

退出条件：

- 连续 2 周或不少于 100 个告警事件完成影子评估。
- 服务/责任团队建议准确率不低于 95%。
- 严重度不得出现危险降级；对无法判断的告警明确标注不确定。
- 影子运行不增加原告警链路的投递延迟和可用性风险。

#### C. L2 协同分诊

开发任务：

- 将建议嵌入工作台或现有事件管理入口，并提供确认、修改、忽略和反馈。
- 对重复事件复用已有调查，对 resolved/reopened 维护同一事故时间线。
- 通过服务端权限控制谁可以创建、重跑、取消和查看调查。
- 提供一键回退到原告警流程的功能开关。

阶段目标：在不降低召回率的前提下减少人工上下文收集时间。

退出条件：值班团队确认使用；分诊人工修正率低于 10%；MTTA 相比基线降低至少 20%；无越权数据访问事件。

### 4.2 SC-02：多源故障调查与根因假设

#### A. 调查策略产品化

开发任务：

- 删除对 `testbed_http_server_requests_total` 等测试床命名的运行时依赖。
- 引入版本化 `ServiceInvestigationProfile`，配置每个服务的 SLI、标签映射、日志选择器、Trace 查询模板、依赖和时间窗。
- 建立查询策略注册表；查询只能由受审查模板生成，模型不能提交任意 PromQL/LogQL/TraceQL。
- 为证据增加环境、租户、数据分类、新鲜度、查询版本和访问策略元数据。
- 引入每数据源并发、QPS、扫描范围和成本预算，避免调查反向压垮监控系统。
- 连接器支持分页、截断、部分结果和稳定错误分类；连接健康状态可见。

阶段目标：同一个工作流能在不改代码的情况下适配首期服务，同时保持固定工具和查询边界。

退出条件：首期每个服务均有通过审核的调查 Profile；越权标签/时间窗查询 100% 阻断；监控数据源压力在约定预算内。

#### B. 真正的假设验证

开发任务：

- 将 `next_checks` 转为受控 `VerificationPlan`，仅允许引用查询策略注册表中的检查。
- 每个高置信假设至少要求两个独立信号，或一个确定性变更事实加一个影响信号。
- 主动寻找反证；区分 supported、contradicted、inconclusive 和 stale。
- 置信度由模型分值、证据可靠性、独立性、新鲜度和反证共同校准，不能直接展示模型原始自评分。
- 对数据源缺失、时间不一致、证据冲突和预算耗尽提供明确原因码。
- 证据引用链接跳转到受权限保护的原查询或快照，保留内容哈希。

阶段目标：验证不再等价于“引用 ID 存在”，而是执行独立检查并能否定错误假设。

退出条件：

- 高置信根因 100% 满足证据独立性规则。
- 未知证据 ID、过期证据和跨环境证据 100% 被拒绝。
- 每个候选假设都能展示支持证据、反证、未完成检查和置信度组成。
- 任一核心数据源不可用时系统完成降级报告，不伪造成功。

#### C. L1 生产影子调查

开发任务：

- 从首期团队选取不少于 30 个已复盘历史事故，脱敏并标注根因、关键证据和合理的不确定答案。
- 在线影子调查只读生产数据，结果不推送到正式事件频道，不触发任何外部变更。
- 由至少两名有经验值班人员盲审 Top-3、证据支持度、错误严重度和实际帮助度。
- 按故障族、服务、数据源覆盖率、模型/Prompt/策略版本分别统计，不只看总平均值。
- 对模型版本、查询模板和数据源变更执行回放和小流量 canary。

阶段目标：用真实数据证明系统在首期边界内可靠，而非沿用测试床的 100% 指标。

退出条件：

- Top-3 可接受根因召回率不低于 85%，Top-1 不低于 65%。
- 关键陈述有效证据支持率不低于 95%，危险无依据陈述为 0。
- 不确定/数据不足场景的保守拒答率达到评审预期，不以强行猜测换准确率。
- 调查完成率不低于 95%，P95 在约定模型和数据源下不超过 120 秒。

#### D. L2 协同调查

开发任务：

- 支持值班人员追加范围、选择候选假设、要求验证和标记无关证据。
- 对关键证据显示查询条件、时间范围、来源、采集时间和截断状态。
- 与现有事件入口双向关联，但系统不可自动关闭事故或覆盖人工结论。
- 建立错误反馈 SLA：错误高置信结论可快速下线对应模型、Prompt 或调查 Profile。

阶段目标：系统成为值班人员的证据工作台，而不是孤立的聊天页面。

退出条件：首期值班人员周活跃使用率不低于 70%；证据准备时间降低至少 30%；错误高置信结论率低于 2%；功能开关回退演练通过。

### 4.3 SC-03：变更关联与回退建议

#### A. 统一变更时间线

开发任务：

- 用真实发布平台和 Git API 替换本地 JSONL 与本地仓库读取。
- 定义 `ChangeEvent` 契约，覆盖部署、镜像、配置、Feature Flag 和基础设施变更，首期只实现部署与代码元数据。
- 为事件保存服务、环境、版本、提交、操作者、流水线、开始/完成时间和可验证来源。
- 建立服务版本到 Pod/ReplicaSet、Commit 和 Trace resource attributes 的关联。
- 只读取必要的 Commit 元数据和文件统计；源代码正文默认不发送给模型。

阶段目标：可以回答“故障窗口前后发生了什么变化”，且时间线来自可信系统记录。

退出条件：首期服务发布事件采集完整率不低于 99%；事件端到端延迟 P95 小于 60 秒；跨环境变更不会被错误关联。

#### B. 影子相关性分析

开发任务：

- 基于时间距离、服务/依赖关系、版本分桶 SLI、异常首次出现时间和历史回退结果计算确定性特征。
- 模型只解释和排序已有相关性特征，不凭提交信息直接判定根因。
- 明确区分“时间相关”“证据支持的因果候选”和“已验证根因”。
- 用历史发布回归和正常发布同时评测，防止所有事故都归因于最近变更。

阶段目标：对发布回归提供高召回，同时保持可接受的误报。

退出条件：发布回归召回率不低于 90%；正常发布错误归因率低于 10%；所有变更结论可回到发布记录与影响证据。

#### C. L2 回退建议

开发任务：

- 展示候选回退版本、变更范围、已知风险、前置检查、验证指标和人工执行入口。
- 建议中必须包含“不回退”备选方案和触发/停止条件。
- 建议与实际执行完全解耦；进入 SC-06 前只记录人工是否采纳及结果。

阶段目标：帮助值班人员更快形成安全处置计划，不自动执行回退。

退出条件：回退建议 100% 包含目标版本、依据、验证和退出条件；不存在无法定位来源的版本；采纳结果进入后续评测。

### 4.4 SC-04：恢复验证与事故收口

#### A. 恢复判据产品化

开发任务：

- 为每个服务定义版本化恢复策略：关键 SLI、基线窗口、最短稳定窗口、告警状态和依赖健康。
- 记录处置前、处置后和稳定窗口证据，区分恢复、未恢复、反复和无法判断。
- 禁止只用单点即时 PromQL 判断恢复；要求区间查询和最小样本量。
- 将验证查询与动作目标、环境和调查绑定。

阶段目标：恢复判断来自预先审核的服务 SLO，而不是 Web 拼装的一条通用查询。

退出条件：首期服务恢复策略审核率 100%；无数据和样本不足时不会报告已恢复；验证结果可重放。

#### B. L2 协同收口

开发任务：

- 展示恢复观察倒计时、残余告警、尚未验证的依赖和回退建议。
- 由事件负责人确认恢复和关闭；系统仅提供建议状态。
- 对已恢复后再次触发的告警复用同一事故或按规则重开。
- 统计恢复误判、复发率和人工覆写原因。

阶段目标：降低“指标短暂变好即关闭事故”的风险。

退出条件：误报恢复率低于 2%；所有收口均保留人工确认者和恢复证据；重开流程演练通过。

### 4.5 SC-05：事故知识与复盘

#### A. 知识治理

开发任务：

- 知识文档增加 Owner、审批状态、可见范围、有效期、替代版本和删除状态。
- 接入文档源的增量同步；原文权限映射到检索和证据查看，不因向量化绕过 ACL。
- Embedding 模型和维度写入索引版本；模型切换采用蓝绿重建，不混合向量空间。
- 建立过期 Runbook、无 Owner 文档和检索失败的治理队列。
- 将 Prompt Injection、密钥、个人信息和生产标识扫描放在导入边界。

阶段目标：知识库可运营、可追责、可失效，不把仓库中的示例 Markdown 直接当作生产知识源。

退出条件：首期知识 100% 有 Owner 和访问策略；过期文档不会进入默认检索；ACL 绕过测试全部失败。

#### B. 复盘草稿

开发任务：

- 从不可变事件和证据生成时间线、影响、根因候选、处置、恢复和待办草稿。
- 区分系统记录、人工陈述和模型总结；模型不能修改原事件。
- 支持人工编辑、来源回链、敏感字段复核和发布审批。
- 从最终复盘提取可验证评测样本，但必须经脱敏和双人审核后进入数据集。

阶段目标：减少复盘资料整理工作，同时保持最终内容由事故负责人负责。

退出条件：关键时间点引用覆盖率 100%；未经审批草稿不能发布；真实事故进入评测集的授权和脱敏记录完整。

#### C. 反馈闭环

开发任务：

- 将错误根因、缺失证据、无效 Runbook、采纳动作和恢复结果结构化记录。
- 每个反馈关联具体模型、Prompt、调查 Profile、工具和知识版本。
- 建立周度失败分类评审和月度质量趋势报告。

阶段目标：产品通过真实失败持续改进，而不是只累计聊天记录。

退出条件：高严重度错误 100% 可定位版本并进入修复队列；修复必须先通过回放门禁再发布。

### 4.6 SC-06：审批式低风险处置

#### A. L2 建议与演练

开发任务：

- 建立独立于模型的动作目录和策略引擎；每个动作声明资源范围、风险、前置条件、审批角色、维护窗口和最大影响面。
- 首批候选动作仅限可回滚 Deployment 回滚，以及经服务 Owner 批准的重启；扩缩容是否纳入由容量策略评审决定。
- 禁止数据库写入、任意命令、删除资源、网络/安全策略修改和跨命名空间动作。
- 在与生产配置等价的预生产环境开展 GameDay，覆盖超时、响应丢失、执行中宕机、重复提交和回滚失败。
- 审批者必须与发起者分离；高风险事故期间支持全局 kill switch 和动作冻结。

阶段目标：先证明策略、幂等、审计和回滚，而不是证明模型会选择动作。

退出条件：不少于 20 次重复演练；未审批/越权/篡改/重放阻断率 100%；未知执行状态能安全对账；kill switch 演练通过。

#### B. L3 小范围生产试点

开发任务：

- 只对白名单服务和特定环境授予短期最小权限工作负载身份。
- 执行前重新读取资源版本、发布状态、当前 SLI、维护窗口和事故状态；前置条件变化则令审批失效。
- 参数哈希绑定目标、环境、动作、预期版本、验证策略和有效期。
- 执行后进行稳定窗口验证；未恢复时停止后续动作并提示人工回滚，不自动串联新动作。
- 审计事件写入独立、追加式存储，并与身份系统、审批记录和集群审计关联。
- 用功能开关按服务关闭动作，不影响只读调查。

阶段目标：让极窄范围内的人工审批动作可安全执行和完整追责。

退出条件：

- 生产试点期未授权动作和跨作用域访问为 0。
- 100% 执行具有审批人、请求哈希、前后证据、集群审计和最终状态。
- 幂等重试不会造成重复副作用；执行状态未知时 fail closed。
- 每个动作均通过恢复和人工回滚演练，动作失败不影响调查主链路。

#### C. L4 条件自治评审（不在本路线承诺内）

只有同时满足以下条件才另行立项：L3 稳定运行至少两个版本周期；动作成功率和恢复误判满足 SLO；动作前置条件完全确定性；安全评审、业务 Owner 和变更管理方共同批准；有实时熔断和故障预算。任何基于自由文本或模型置信度的高风险自动变更仍然禁止。

### 4.7 SC-07：主动可靠性分析

该场景包括容量预测、性能回归、异常趋势、成本优化和日常巡检。当前暂不开发，触发条件是：SC-01～SC-05 已稳定、服务目录和 SLO 数据质量达标、真实反馈证明用户需要主动分析，并且不会挤占事故响应的可靠性预算。

未来阶段仍应从离线周报和只读建议开始，不直接复用实时事故 Prompt，也不默认授予任何处置能力。

## 5. 共同生产底座

共同底座不是附属工作。阶段 8 未通过时，后续场景只能使用测试或脱敏离线数据。

### 5.1 身份、权限和租户边界

- Web 和 API 接入企业 OIDC/SSO；后端验证 issuer、audience、签名、过期时间和组织声明。
- 建立 `viewer`、`investigator`、`incident-commander`、`approver`、`connector-admin`、`platform-admin`，权限默认拒绝。
- 发起与审批职责分离；平台管理员不默认拥有生产审批权。
- 每个调查携带组织、项目、环境和数据作用域；数据库查询和对象存储访问都执行同一边界。
- Python、Go、迁移任务和连接器使用独立工作负载身份，服务间启用 mTLS；停用共享长效 Token。
- 定义紧急访问流程、短期授权、审批、撤销和季度权限复核。

### 5.2 数据安全与模型治理

- 对告警、日志、Trace、代码元数据、知识、Prompt、模型输入/输出和 Artifact 分级。
- 在数据源侧先过滤和聚合；生产日志原文默认不持久化、不进入模型。
- 配置字段级脱敏、租户专用盐、加密传输、数据库/对象存储 KMS 加密和密钥轮换。
- 明确模型供应商的数据地域、留存、训练使用、子处理方和删除条款；支持关闭某类数据出站。
- Prompt 和工具输出保留脱敏哈希、版本与审计，不在普通日志记录完整敏感上下文。
- 为调查、事件、证据、审计、Artifact、模型记录和评测样本分别定义保留期及删除/法律保留流程。

### 5.3 部署、数据和灾备

- 提供版本化 Helm Chart 或等效部署包，分离 dev/staging/prod 配置。
- Web、Investigation Service 和 Tool Gateway 支持多副本、滚动升级、PDB、拓扑分散、NetworkPolicy 和只读根文件系统。
- PostgreSQL 使用受支持的高可用方案；完成容量估算、连接池限制、慢查询告警和索引治理。
- 引入单一 schema migration 工具；迁移遵循 expand/migrate/contract，不由多个服务启动时建表。
- Artifact 迁移到带版本、加密、生命周期和访问日志的对象存储。
- 定义 RPO/RTO，执行 PostgreSQL PITR、对象存储恢复和区域故障演练。
- 所有组件支持优雅终止；worker 释放或续租明确，变更执行不可因 Pod 退出进入未知副作用。

### 5.4 产品自身可观测性

- 使用标准 W3C Trace Context 和 OTel 打通入口、工作流节点、模型、检索、gRPC、数据源、审批与动作。
- 提供 RED/USE 指标：请求、错误、延迟、队列深度、租约、模型 Token/成本、工具限流、证据缺失、SSE 连接和审批等待。
- `/health/live` 只判断进程；`/health/ready` 检查是否能安全服务；依赖降级通过状态接口和指标表达。
- 建立自身 SLO、告警、仪表盘和 Runbook，避免 Copilot 故障干扰原运维链路。
- 关键日志使用结构化事件和安全错误码，禁止把异常对象、Prompt 或凭据原样写入日志。

### 5.5 供应链与发布

- 锁定依赖并执行 SAST、依赖漏洞、Secret、IaC、容器和许可证扫描。
- 生成 SBOM、签名镜像和构建来源证明；生产只允许受信 registry 和已验证签名。
- 数据集、Prompt、调查 Profile、策略、连接器、模型和 schema 都有独立版本，并进入发布清单。
- 发布采用测试环境回放、影子/小流量 canary、指标观察和自动/人工回退。
- 数据库不可逆迁移、权限扩大、数据出站变化和新变更动作必须单独安全评审。

### 5.6 运营责任

- 明确 Product Owner、平台 Owner、当班支持、数据 Owner、安全审批人和模型质量 Owner。
- 建立 P0/P1 故障响应、模型供应商故障、错误高置信结论、数据泄露和误操作 Runbook。
- 每周评审错误样本与连接器健康，每月评审 SLO、成本、权限、数据留存和模型漂移。
- 产品不可用时原告警和处置流程必须继续工作；Copilot 永远不成为唯一控制通道。

### 6.1 阶段 8：生产准入底座与范围冻结

任务：

- 冻结首期团队、服务、告警、故障族、数据源、环境和不做事项，形成 Owner 签字的场景清单。
- 完成 OIDC/SSO、服务端授权、作用域模型、工作负载身份、mTLS、Secret 管理和轮换。
- 完成数据分类、模型出站评审、脱敏、留存、删除和审计设计。
- 提供版本化数据库迁移；完成 HA PostgreSQL、PITR 和恢复演练。
- 提供生产部署包、多副本、NetworkPolicy、PDB、资源和安全上下文。
- 为产品本身接入 OTel、指标、日志、仪表盘、SLO、告警和 Runbook。
- 把只读工具审计与 Artifact 迁入受控持久存储。
- 建立供应链扫描、SBOM、签名、canary、回滚和配置版本治理。

阶段目标：平台达到“可以安全开始只读影子试点”的条件，而不是直接面向全部用户。

退出条件：安全威胁模型通过评审；越权测试全部通过且越权成功数为 0；备份恢复达到批准的 RPO/RTO；所有生产组件有 SLO 和 Runbook；关键依赖失败时 readiness 正确摘流；无默认开发口令和浏览器自报角色。

### 6.2 阶段 9：单域真实数据影子试点

任务：

- 实现告警源、服务目录、Prometheus、Loki、Tempo、Kubernetes、发布平台和 Git 的生产只读连接。
- 完成首期服务调查 Profile 和恢复策略，移除测试床专用查询。
- 实现告警幂等、聚合、状态更新、风暴保护和队列背压。
- 实现受控 Verification Plan、反证检查、证据新鲜度和置信度校准。
- 建立不少于 30 个脱敏历史事故样本和双人标注流程。
- 影子运行并记录与人工结果的差异，不改变原值班流程。

阶段目标：证明 SC-01～SC-03 在真实数据上的安全性、准确性、时延和成本。

退出条件：满足各场景 L1 指标；无生产数据越权或泄露；产品故障不影响原告警链路；连接器压力不突破数据源预算；Go/No-Go 评审批准进入协同模式。

### 6.3 阶段 10：人机协同只读上线

任务：

- 将工作台接入值班入口，提供可信登录、授权、反馈和审计。
- 支持人工修改范围、触发受控验证、采纳/拒绝假设和标记错误证据。
- 提供来源链接、查询截断/新鲜度、降级和不确定性展示。
- 建立模型、Prompt、Profile 和连接器 canary/回退开关。
- 运行用户培训、值班手册、支持排班和每周失败评审。

阶段目标：让系统实际减少值班人员的信息收集成本，但不拥有生产写权限。

退出条件：连续 4 周达到平台与 AI SLO；MTTA 降低至少 20%，证据准备时间降低至少 30%；错误高置信结论率低于 2%；用户可以在 5 分钟内完成产品回退；原运维流程仍可独立工作。

### 6.4 阶段 11：恢复、复盘与故障族扩展

任务：

- 上线 SC-04 恢复观察和人工收口。
- 上线 SC-05 复盘草稿、知识审批、ACL 同步和反馈入库。
- 在 F1/F2 连续两个周期达标后加入 F3 资源饱和；新增独立数据集和指标。
- 评估第二个团队，但不同时增加新团队、新环境和新故障族。

阶段目标：形成只读事故生命周期闭环，并用真实反馈驱动质量改进。

退出条件：恢复误判率低于 2%；复盘关键事件引用覆盖率 100%；知识 ACL 测试全部通过；F3 独立指标达标；扩展不降低 F1/F2 指标或平台 SLO。

### 6.5 阶段 12：审批式低风险处置试点

任务：

- 完成动作目录、策略引擎、职责分离、变更窗口、kill switch 和不可篡改审计。
- 在预生产执行至少 20 次 GameDay，并覆盖未知执行状态与失败回滚。
- 选择 1～2 个低 Tier、可快速回滚、Owner 明确的白名单服务进入 L3。
- 生产执行采用显式人工发起和独立审批，不允许模型自动发起审批请求。
- 观察动作成功、未恢复、回滚、人工中止和误建议，按动作类型独立评审。

阶段目标：验证低风险动作的治理闭环，不以扩大动作数量为目标。

退出条件：满足 SC-06 L3 全部门槛；安全、业务、平台三方批准；任一安全强制项失败立即关闭全部生产动作但保留只读能力。

### 6.6 阶段 13：规模化与条件自治评审

只有出现真实瓶颈才引入新基础设施：

- 数据库租约和 worker 无法满足容量/SLO 时，再评估专用队列。
- 跨天长流程和复杂补偿无法被现有检查点表达时，再评估 Temporal 等工作流引擎。
- PostgreSQL 检索无法满足规模或语言质量时，再评估独立搜索系统。
- 单工作流在评测中出现可复现的上下文/隔离瓶颈时，再评估子图或多 Agent。
- 多团队出现硬隔离需求时，再建设完整多租户控制面。

阶段目标：以观测到的容量、可靠性和组织需求驱动演进，避免提前平台化。

## 8. 生产准入指标与门禁

以下是初始建议值。阶段 8 必须结合流量、事故基线和团队风险偏好冻结正式 SLO。

### 8.1 平台门禁

| 指标 | L1/L2 建议门槛 | L3 附加门槛 |
| --- | ---: | ---: |
| API 可用性 | 月度 >= 99.9% | 月度 >= 99.95% |
| 调查创建成功率 | >= 99.5% | >= 99.5% |
| 调查完成率 | >= 95% | >= 95% |
| 调查端到端 P95 | <= 120 秒 | <= 120 秒 |
| 告警接入延迟 P95 | <= 10 秒 | <= 10 秒 |
| Trace 完整率 | >= 99% | 100% 覆盖变更链路 |
| 审计写入成功率 | >= 99.99% | 100%；失败则禁止动作 |
| 备份恢复 | 达到批准的 RPO/RTO | 同左，且动作状态可对账 |
| 越权访问/未授权动作 | 0 | 0 |

### 8.2 AI 与证据门禁

| 指标 | 建议门槛 | 说明 |
| --- | ---: | --- |
| Top-1 可接受根因准确率 | >= 65% | 按故障族分别计算 |
| Top-3 可接受根因召回率 | >= 85% | 允许“不足以判断”作为正确答案 |
| 关键陈述有效证据支持率 | >= 95% | 来源存在、可访问且支持陈述 |
| 危险无依据陈述 | 0 | 涉及影响、根因、恢复和变更的错误高置信陈述 |
| 跨租户/跨环境引用 | 0 | 强制安全门禁 |
| 高置信错误结论率 | < 2% | 必须按服务和故障族拆分 |
| 保守降级正确率 | 100% | 数据缺失时不得伪造成功 |
| Prompt Injection 越权成功 | 0 | 强制安全门禁 |

### 8.3 业务效果指标

- MTTA、证据准备时间和首次可执行建议时间相对试点前基线的变化。
- 值班人员建议采纳率、人工修正率、绕过率和帮助度评分。
- 重复告警压缩率及误聚合/漏聚合率。
- 恢复误判率、事故重开率和复盘准备耗时。
- 单调查模型成本、数据源查询成本及每日/团队预算使用率。

业务指标只用于判断产品价值，不能抵消安全门禁失败。安全门禁失败时，即使 MTTR 显著降低也不得继续扩大流量或权限。

## 9. 发布、回退与停止条件

### 9.1 发布单位

每次候选发布必须绑定：

- 源码 Commit、容器 digest、SBOM、签名和构建证明；
- 数据库 schema、Proto/API、调查 Profile、连接器和策略版本；
- Prompt、模型/供应商、Embedding、知识索引和评测集版本；
- 离线回放、影子/canary 报告、已知失败和批准人。

### 9.2 分级发布

1. 冻结数据离线回放。
2. 预生产集成与故障演练。
3. 生产 L1 影子流量，不对用户展示。
4. 少量用户 L2 canary，保留原流程。
5. 单团队 L2 全量。
6. SC-06 单独走 L3 变更发布链路。

任何阶段只能逐级晋升，不能从离线评测直接进入生产协同或生产动作。

### 9.3 立即停止条件

出现下列任一情况，自动或人工将系统降为只读、影子或完全旁路：

- 未授权数据访问、跨租户证据、敏感信息外泄或 Prompt Injection 导致越权。
- 未审批生产动作、参数/目标不一致仍执行、幂等失效或动作状态无法对账。
- 审计、策略引擎、身份提供方或数据库不可用且系统无法安全降级。
- 危险无依据陈述、错误恢复判断或高置信错误结论突破冻结门槛。
- Copilot 对原告警、监控或 Kubernetes API 造成明显资源压力。
- 新版本核心指标回归且无法在规定时间内解释。

回退必须按层独立：模型/Prompt 回退、调查 Profile 回退、连接器关闭、场景关闭、生产动作全局关闭和整个产品旁路。关闭 AI 不应阻断原有告警与人工运维流程。

## 12. 开工顺序

推荐按以下顺序进入实现：

1. 评审并冻结首期试点边界，不先写新连接器。
2. 完成 PROD-001～007 的生产底座，并通过阶段 8 门禁。
3. 并行推进告警/服务目录（PROD-008/009）和只读连接器/验证（PROD-010/011）。
4. 建立真实事故评测（PROD-012），先离线，再影子。
5. 影子达标后实施协同工作台（PROD-013），完成阶段 10。
6. 再做恢复、复盘和第三故障族（PROD-014/015）。
7. 最后单独评审并实施生产处置（PROD-016/017）。

阶段 8 的第一个交付物应是“试点范围、身份边界、数据边界和 SLO 决策”，而不是 Kubernetes YAML 或更多 Agent 工具。只有这些边界被业务、SRE、安全和平台共同确认，后续任务才能形成可验收的生产开发计划。
