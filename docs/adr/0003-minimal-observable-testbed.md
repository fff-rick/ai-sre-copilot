# ADR-0003：自建最小可观测测试床

- 状态：Accepted
- 日期：2026-09-02

## 判断

阶段 1 使用一个可配置 Go 镜像运行 API、订单、库存和支付四个角色，并使用独立 PostgreSQL 组成五服务业务链路。遥测通过 OpenTelemetry Collector 分发到 Prometheus、Loki 和 Tempo；cAdvisor 仅负责补足容器 CPU 与内存 Ground Truth。

## 比较

| 方案 | 复杂度 | 故障可控性 | 与 V1 边界匹配 | 决策 |
|---|---:|---:|---:|---|
| 完整 OpenTelemetry Demo | 高 | 中 | 低 | 不采用；包含超出 V1 的语言和中间件 |
| 每个服务独立仓库/实现 | 高 | 高 | 中 | 不采用；重复脚手架多于业务价值 |
| 一个二进制、四个运行角色 | 低 | 高 | 高 | 采用 |

## 约束

- 业务流固定为 `API -> Order -> Inventory/PostgreSQL + Payment`。
- 故障必须有最大持续时间、参数上限、显式恢复和 Ground Truth。
- CPU 与内存使用真实但有界的进程内负载，并受 Compose 资源上限约束；不主动触发 OOM。
- 连接池场景必须实际占用 pgxpool 连接；依赖与配置场景必须进入真实 HTTP 客户端路径。
- 发布回归必须记录前后版本且只影响明确输入，不能退化为另一种 100% 错误率场景。
- 故障控制接口不映射到宿主机，且要求测试专用控制头。
- 阶段 1 的数据库和网络与 AI-SRE 领域数据库隔离。
- 测试床不得引入 Kafka、服务网格或 Kubernetes；这些组件不能改善当前验收指标。

## 后果

共享二进制降低维护成本，但不用于模拟不同语言运行时特有故障。后续只有在某类 Ground Truth 明确依赖特定运行时行为时，才新增专用服务实现。
