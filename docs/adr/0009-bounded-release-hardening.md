# ADR 0009：阶段 7 使用有界 Worker Pool 与可证明发布清单

- 状态：Accepted
- 日期：2026-09-04

## 判断

推荐在现有 PostgreSQL 租约队列上增加 5 worker 的有界并发，不引入 Kafka、Redis、Celery 或
Temporal。推荐把评测报告通过只读、白名单 API 提供给 Web，而不是让浏览器直接读取 Artifact。
正式发布使用 Git Tag、内容哈希 manifest 和构建证明绑定源码与评测输入。

## 决策

1. Investigation Service 默认启动 5 个 worker，配置范围固定为 1～16；每个 worker 独立领取、
   续租和释放任务。
2. Compose 对四个产品服务设置 CPU、内存、PID 和 `no-new-privileges`，资源结果只作为同环境
   回归基线，不宣称生产容量。
3. 最新评测接口只返回质量指标、版本哈希和失败类别；拒绝超限、缺失或 Schema 无效文件。
4. 发布候选生成 manifest，绑定 Commit、Tag、运行时、故障数据集、检索集、Prompt、模型、
   数据库 Schema、Compose 和离线/在线报告哈希。
5. 正式 Tag 必须重新执行 32 用例真实模型评测；缺少模型凭据或价格配置即停止发布。
6. 演示保留单源不可用和未审批执行阻断路径，不把所有失败隐藏成成功画面。

## 被否决方案

- 引入消息队列实现五并发：现有租约队列已满足规模，新增组件只扩大故障面。
- Web 直接挂载/读取 JSON：会泄漏绝对路径、工具录制引用和内部检查点信息。
- 在 PR 提交上提前打正式 Tag：Tag 会绑定未合并代码，无法代表主分支发布状态。
- 仅用离线回放发布：可验证管线，但不能证明真实模型质量、延迟和成本。

## Trade-off

单机 worker pool 不能跨区域弹性扩缩容，PostgreSQL 仍是单点；但 V1 的目标是五并发、恢复和安全
演示，这一方案最小且可验证。在线评测让发布依赖模型凭据和费用，换来发布声明的真实性。
