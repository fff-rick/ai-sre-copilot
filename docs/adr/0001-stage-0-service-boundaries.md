# ADR-0001：阶段 0 服务边界与延迟引入依赖

- 状态：Accepted
- 日期：2026-09-02

## 背景

项目文档提出 Python 智能面、Go 可信工具面和 TypeScript 交互面的三语言架构。当前仓库仍处于纯文档状态，尚无需要恢复的调查、外部连接器或审批变更。

## 决策

阶段 0 保留三种语言及进程边界，但只实现健康检查、领域端口、Fake 适配器、构建、测试和本地编排。

- Python 服务拥有调查领域状态和模型端口，不持有运维系统凭据。
- Go 网关拥有工具注册与执行端口，不包含模型调用或根因判断。
- Web 仅调用 Python API，不直接访问 Go 网关。
- PostgreSQL 在本地环境启用 pgvector 扩展，但阶段 0 不创建业务表。
- LangGraph、gRPC 生成代码、OpenTelemetry 全栈和真实连接器按路线图在解决实际用例时引入。

## 比较

| 方案 | 复杂度 | 边界验证 | 首阶段反馈速度 | 决策 |
|---|---:|---:|---:|---|
| 单一 Python 服务 | 低 | 弱 | 快 | 不采用；无法尽早验证高权限隔离边界 |
| 三语言并立即接入全部组件 | 高 | 强 | 慢 | 不采用；空骨架的依赖和故障面过大 |
| 三语言薄骨架、按阶段增加能力 | 中 | 强 | 中 | 采用 |

## 后果

首阶段承担多工具链维护成本，但能在业务代码增长前固定信任边界。延迟引入不是否定 LangGraph 或 gRPC；它避免在缺少可执行验收用例时过早固化框架细节。
